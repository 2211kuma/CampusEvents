# 实验二教师专用材料：隐藏需求变更与授课提示

| 重要：教师保密内容<br>本材料用于授课准备。建议教师只在实验二初始版本通过验收、已保存baseline-v1后发布CR-01和CR-02。将指导书发给学生时，不附带本材料。 |
| --- |

## 一、需求变更单CR-01：新增年级限定报名

变更背景：学校新增仅面向大二、大三学生的活动类别。

具体要求：Activity支持“年级限定直接报名”规则；Student新增grade字段，值为1—4。仅grade∈{2,3}的学生可以报名此类活动，其他年级收到明确提示。该规则同时遵守名额限制、活动开始时间和重复报名等公共约束。原有“直接报名”和“审核报名”行为不得改变。

期望设计：学生可以通过新增独立策略实现或采用可组合规则设计，但应解释设计选择；尽量不修改RegistrationService的核心流程。是否通过“新增策略而不修改核心服务”不是唯一评分标准，应结合原系统设计决定。

| 变更测试 | 输入 | 期望 |
| --- | --- | --- |
| CR1-01 | 大二学生报名年级限定活动 | 通过 |
| CR1-02 | 大三学生报名年级限定活动 | 通过 |
| CR1-03 | 大一学生报名年级限定活动 | 拒绝并显示原因 |
| CR1-04 | 大四学生报名年级限定活动 | 拒绝并显示原因 |
| CR1-05 | 变更后重新运行C1—C10 | 全部原有用例保持通过 |

## 二、需求变更单CR-02：新增邮件通知

变更背景：管理员希望在站内消息之外，同步向报名学生发送邮件通知。出于教学便利，不接入真实邮件服务器，由教师或学生提供的MockEmailSender模拟发送，记录收件人、主题、内容、状态与时间。

具体要求：对于报名通过、审核通过或拒绝的事件，原有站内通知继续运行，同时新增模拟邮件发送。邮件发送故障必须记录错误，但不得错误回滚已成功提交的报名。应避免同一业务事件被重复发送两次。

期望设计：使用观察者模式或事件通知结构新增邮件订阅者/处理器，不要求把邮件发送代码直接写入RegistrationService。

| 变更测试 | 输入 | 期望 |
| --- | --- | --- |
| CR2-01 | 直接报名通过 | 站内消息和模拟邮件均有记录 |
| CR2-02 | 审核批准或拒绝 | 两种渠道记录对应结果 |
| CR2-03 | 模拟邮件发送失败 | 报名状态正确、错误有日志 |
| CR2-04 | 重复提交同一业务动作 | 不应重复生成多份相同通知 |
| CR2-05 | 变更后重新运行C1—C10 | 原有功能保持通过 |

## 三、推荐授课组织方式

1、第2周发布初始SRS，学生绘制UML类图；教师用10分钟检查职责划分和模式选择理由。

2、第2周验收初始版本并核对baseline-v1存在；未达到核心功能的小组优先修复最小可行版本。

3、第3周在课堂同时发布CR-01与CR-02，要求先交影响分析、后进行AI修改。

4、第3周统一回归测试、收集代码差异。

## 四、教师评价提示

重点看学生的设计理由和证据，不把“使用某个固定模式”作为唯一正确答案。对比实验可以由教师选择少数小组开展，避免每组都维护两套完整系统造成工作量超标。
