# 变更影响分析（CR-01 / CR-02）

项目：CampusEvent 校园活动报名与管理系统
基线版本：baseline-v1（8 项功能，C1–C10 全通过，已部署 http://43.142.137.39）
变更版本：change-v2
分析日期：2026-11-26

---

## 1 变更请求摘要

| 编号 | 变更内容 | 验收要点 |
|---|---|---|
| CR-01 | 新增“年级限定直接报名”：仅大二、大三可报名，其他年级明确提示原因；名额、时间、重复报名规则不变；原有直接报名与审核报名行为不变 | 新增独立策略类；尽量少改 `RegistrationService`；CR1-01~05 |
| CR-02 | 报名通过、审核通过、审核拒绝三类事件，在站内消息之外增加模拟邮件（记录收件人、主题、内容、状态、时间）；失败留痕但不回滚；同一业务事件不得重复发送 | CR2-01~05；重跑 C1–C10 |

## 2 影响分析

### 2.1 CR-01 年级限定

| 受影响对象 | 影响类型 | 说明 |
|---|---|---|
| `PolicyType`（entities.py） | 修改（枚举扩展） | 新增 `GRADE_LIMITED`，标签“年级限定直接报名（大二、大三）” |
| `Student`（entities.py） | 修改（属性扩展） | 新增 `grade:int=1` 与 `grade_label`；老代码构造 `Student(id, name)` 仍可用（默认年级 1） |
| `errors.py` | 新增类 | `GradeNotAllowedError`，默认文案“该活动仅限大二、大三学生报名” |
| `policies.py` | 新增类 + 微调 | 新增 `GradeLimitedRegistrationPolicy`，在 `PolicyRegistry` 注册第三策略；`PolicyContext` 增加可选 `student` 字段（默认 None，不破坏原有调用） |
| `RegistrationService.register` | 修改 1 处 | 构造 `PolicyContext` 时多传 `student=student`，业务判定仍全部交给策略，服务层零分支新增 |
| `repositories.py` | 修改 | `students` 表加 `grade` 列；`_migrate()` 用 `PRAGMA table_info` 判断后 `ALTER TABLE` 补列，老库无需重建；`StudentRepository.get/list_all` 带出年级 |
| 演示数据 | 修改 | 新增四名不同年级学生（S001 大二 / S002 大三 / S003 大一 / S004 大四）及一个年级限定活动 |
| 页面 | 修改 | 新建活动下拉增加“年级限定直接报名”；账号切换显示年级；拒绝原因经 flash 呈现 |

### 2.2 CR-02 模拟邮件

| 受影响对象 | 影响类型 | 说明 |
|---|---|---|
| `email_outbox` 表 / `EmailRepository` | 新增 | 字段：event_id、收件人、主题、正文、状态、说明、时间；索引 event_id |
| `MockEmailSender` | 新增类 | 不接真实 SMTP，可配置对指定学号模拟失败（用于 CR2-03 演示与测试） |
| `EmailNotificationObserver` | 新增类 | 只订阅“报名通过 / 审核通过 / 审核拒绝”三类事件；先经事件总线派发，不侵入服务层 |
| `InAppNotificationObserver` | 修改 | 幂等键由 `event_id` 改为 `event_id:inapp`，与邮件渠道 `event_id:email` 隔离，避免两渠道互相“吃掉”事件 |
| `EventBus` | 修改 | 失败留痕的渠道名改取订阅者的 `channel` 属性（`inapp` / `email`），日志可读且可统计 |
| `build_services` | 修改 | 装配邮件渠道，支持注入自定义发送器；`Services` 增加 `emails` 仓储 |
| 页面 | 新增 | `/admin/emails` 展示发件箱与通知失败记录 |

### 2.3 未受影响 / 明确保持不变

- `ActivityService` 的全部校验（名称、容量、开始时间、删除保护）不变。
- `DirectRegistrationPolicy`、`AuditRegistrationPolicy` 的判定逻辑不变，C1–C10 行为不变。
- 名额检查仍为公共规则 `CapacityRule`，策略只决定“通过 / 待审核 / 拒绝”。
- 数据库其余表结构与既有数据不变，只做增量加列与加表。

## 3 风险与应对

| 风险 | 影响 | 应对措施 |
|---|---|---|
| 老库无 `grade` 列，直接上线报 `no such column` | 现网库启动失败 | `_migrate()` 检测并 `ALTER TABLE` 补列，默认年级 1；已在本地老库上验证可启动 |
| 两渠道共用同一幂等键 | 后订阅的渠道被跳过，或删除一个渠道导致另一个渠道丢通知 | 幂等键按渠道加后缀，`processed_events` 记录 `事件:渠道` |
| 邮件渠道异常向上冒泡 | 报名成功却被“回滚”或报错 | 事件总线隔离异常并写 `notification_failures`；发件箱另存 `failed` 记录，报名状态不回滚 |
| 年级判断写在服务层 | 违反“策略模式”设计约束，后续加规则继续膨胀 | 判定全部落在 `GradeLimitedRegistrationPolicy`，服务层只传上下文 |
| 年级限定与名额判定顺序错乱 | 满员与年级不符时提示信息误导 | 策略内先校验年级再校验名额，提示按“最直接原因”给出 |
| 模板硬编码“大二、大三” | 文案与策略常量漂移 | 提示文案集中在 `GradeNotAllowedError` 与策略内，页面只展示策略标签 |
| 重复提交/网络重试 | 重复邮件、重复站内消息 | 幂等键占用失败即跳过；CR2-04 以重复派发同一事件验证 |

## 6 结论

两项变更均为“扩展式”改动：CR-01 通过新增独立策略类实现年级约束，未在服务层引入条件分支；CR-02 通过新增订阅者与仓储实现第二通知渠道，并以渠道级幂等键保证不重复。基线功能与数据库存量数据保持兼容，可进入 `change-v2` 分支交付并在服务器增量部署。
